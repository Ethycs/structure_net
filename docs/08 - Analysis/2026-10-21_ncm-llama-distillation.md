# Llama-to-NCM distillation: smaller and faithful, speed target unmet

Completed exploratory model study `llama32-3b-ncm-distillation-v1`, classified
`distilled_quality_retained_speed_target_unmet`, and frozen-runtime follow-up
`llama32-3b-ncm-graph-runtime-v1`, classified `speed_target_unmet`. Both are
tested, underpowered and `confirmed:false`.

A **148,649,225-parameter NCM** adapted on actual Llama-3.2-3B-Instruct summaries
passed **100/100** fresh synthetic source-fidelity cases. GPU graph replay
retained every native output ID in all300 comparisons and measured
**81.89 common output tokens/s**, versus original Llama's **77.21**. Its runtime
weight/buffer storage is **713,294,288 bytes**, about **9.01x smaller** than the
original FP16 teacher. The planned 2x speed goal was not met. The existing
factorized FP16 model remained faster, but passed only93/100 cases here.

preceded adaptation outcomes. The separate

The method is [Next-Concept Modeling](https://arxiv.org/abs/2610.14162), using the
[official HazyResearch implementation](https://github.com/HazyResearch/ncm),
commit `c70274273f489abc73832b2b98584a8483b6b203`, and
[released XSum components](https://huggingface.co/hazyresearch/ncm-checkpoints),
revision `d342ce8aaea58830eef3b8ad473664673e41f692`. NCM learns a hierarchy of
discrete text codes, predicts each level's positions in parallel, then decodes
the complete hierarchy to text. The paper's headline speed comparisons are
against diffusion models, not evidence of a31x advantage over Llama. This
experiment is a task-specific sequence-distillation adaptation, rather than a
reproduction of the paper's full training or published XSum evaluation.

The released configuration has a512-position GPT-2 source prefix and48-position
output canvas. Its actual nine levels are4/6/10/14/20/26/32/40/48, totaling200
code positions. Each request includes nine generator passes and the text
decoder. The generator has88,015,881 parameters and the codec60,633,344.
Both start from released weights; there is no random weight reinitialization
or direct conversion of Llama's parameter matrices. Encoder and codebooks stay
frozen. This representation is not a generally lossless compression of Llama
or a transfer of all of its capabilities.

Training targets were generated by the cached, original full28-layer FP16
Llama-3.2-3B-Instruct, pinned to snapshot
`0cb88a4f764b7a12671c53f0838cd831a0843b95`. Physical readback verified its seven
manifest files. Its CUDA-graph/FlashAttention/current-prompt lookup runtime
passed a separate token-parity check against Hugging Face greedy generation.
All1188 teacher generations completed; all1024 training labels preserved the
required facts and fit47 GPT-2 tokens plus EOS. No label was replaced with a
template reference, rejected and resampled, or truncated. Because Llama tokens
and NCM codes have different vocabularies, supervision is generated text
encoded into the frozen hierarchy followed by code cross-entropy, not logit KL.

Data contains1024 training,64 development and100 held-out sources, with seeds
starting610000/620000/630000. Every complete source has a distinct hash. The
four balanced families are raw256/384/480 GPT-2 tokens and hierarchy-like384
tokens. Actual sources span256–493 GPT-2 tokens and at least192 Llama tokens;
none was truncated. Each contains provisional owner/budget/deadline proposals,
irrelevant discussion and an explicit superseding final decision. These are
synthetic final-decision summaries with familiar names and templates, including
copy-heavy hierarchy fixtures, not production raw/merge data.

There are1007 unique training fact tuples,63 development tuples and100 held-out
tuples. Two development and six held-out tuples also occur in training, with
different source texts. Thus all held-out sources are new, while94/100 of their
joint fact combinations are new. Individual names, projects, amounts and dates
come from the same bounded vocabulary. No unseen-name or topic-shift claim is
made. The final sources were fixed before adaptation and were not used for
gradient updates or checkpoint selection.

The pretrained codec reconstructed the final facts in53/64 development teacher
summaries. The planned decoder-only repair used512 updates, batch16, AdamW
lr2e-4, betas(.9,.95), weight decay.01 and clip1. Encoder, codebooks and
reconstruction operators remained frozen, with a verified unchanged digest.
Both the256- and512-update checkpoints reached64/64; step512 won the fixed
cross-entropy tie-break. This is observed reconstruction fidelity, not a
universal losslessness guarantee.

With that codec frozen, the generator trained for1024 updates, batch8, AdamW
lr1e-4 with50 warmup steps and cosine decay to1e-5, betas(.9,.95), weight
decay.01 and clip1. It used dropout.1, BF16 autocast and FP32 master weights.
The loss weights code positions equally and includes learned level0 queries.
Each level sees only prior-level reconstructions; CPU tests verify that its
own and future target codes cannot leak into predictions. No conditioning-code
corruption or additional neighborhood objective was added in this pilot.

Seventeen distinct focused CPU tests passed across scoped invocations. They
cover fixed configuration, split/source binding, target capacity without
truncation, objective routing, target-code leakage, quality/speed decisions,
review integrity, graph I/O, source-copy identity and top1 tie behavior. The
full-architecture CUDA lifecycle passed real decoder/generator backward
updates, exact checkpoint reload, batch16/batch8 memory and inference checks.
Its peak allocation was4.35GB; full codec and generator adaptation peaked at
1.18GB and4.84GB, respectively. Systems checks are not model-quality evidence.

The model-study timing blocks ran adapted NCM, original teacher, existing
factorized rank1024 FP16 Llama, then released NCM. Each used all100 final cases,
three timed repetitions and an excluded warmup per case. CPU-input-token-IDs
through decoded CPU text is the measurement boundary. Loading, compilation,
setup and warmups are excluded. Each architecture receives its native encoding
of the same complete source; Llama also receives its summary chat instruction.
Output counts use the common Llama tokenizer, not the200 latent code positions.
Released NCM uses the same unpenalized greedy policy as adapted NCM; this is not
the paper's frequency/adjacency-penalized evaluation configuration.

Source grading uses Codex review with exact final-source quotations, aided by
project/owner/budget/deadline/supersession/length checks. No independent judge
model was used. Every adapted summary preserves the final facts without extra
assertions. Teacher outputs are identical to them in95/100 cases; five shorter
owner/budget/deadline lists are also faithful. The factorized model omits Leo
Grant in seven cases:630020/630050/630060/630061/630076/630094/630098. Released
NCM never identifies the required owner and generally produces unsupported
news-style text. Its longer output token count does not establish capability.
All four conditions were text-stable across repetitions.

The eager model retains quality but has latency/token-rate ratios0.45059x and
0.45445x against original Llama, below the2x gate. Its result remains
`distilled_quality_retained_speed_target_unmet`.

The separately scoped graph follow-up preserves weights and the nine-level
schedule. Capture first failed on CPU-to-CUDA scalar allocations, then on
PyTorch2.4's native categorical sampler. Both failed systems roots and complete
logs remain immutable. The
[scalar amendment](../07%20-%20Status%20Reports/2026-10-21_ncm-graph-capture-amendment.md)
replaces only two scalar allocations with equivalent GPU fills. The
[sampler amendment](../07%20-%20Status%20Reports/2026-10-21_ncm-graph-sampler-amendment.md)
implements the same fixed top_k1 law via GPU inverse CDF, including uniform ties.
This preserves prediction probabilities, not a promise of identical RNG streams
on every hypothetical tie. It adds no optimizer update. The pinned official
repository is unchanged, and the copied method's MIT notice is included.

The corrected graph pilot passed11 original-eager comparisons, including
A/B/A reset. The final runtime matched all48 native output IDs and text in all
300 saved eager/graph pairs. It inherits their source decisions by exact
text/source identity. These100 inputs are used runtime-validation sources,
not an additional independent model-quality holdout. The nearby parent timing
controls are explicitly reused:900 control cells, with verified fingerprints,
source/model identities and raw output files. Sequential block order, time
drift and the lack of randomized repetitions remain limitations.

Graph replay improves both NCM speed endpoints **2.33407x** over eager execution.
Against original Llama, its request-latency ratio is **1.05172x** and common
token-rate ratio **1.06072x**. Against the factorized control, they are
**0.64243x** and **0.59380x**. The2x original-Llama gate still fails, so the
graph classification is `speed_target_unmet`. It is not a2x Llama acceleration.
Code inspection shows that the source prefix is still recomputed at every
level; reuse of source representations within one request is an untested next
optimization, not a measured result here.

The inference entry point defaults to the validated graph runtime:

```bash
CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=0 OMP_NUM_THREADS=2 \
HF_HUB_OFFLINE=1 LD_LIBRARY_PATH='' \
data/experiments/moba_paper/environment/bin/python \
  -m experiments.structure_net.infer_ncm_llama --input /path/to/source.txt
```

Use `--runtime eager` for the original execution path. Nonempty input exceeding
512 GPT-2 tokens is rejected, with no silent truncation. A development-source
CLI demonstration is saved under `20261021_demo_v1`, outside the benchmark.
Reproduction uses `run_ncm_llama` for data, targets, pilots and adaptation,
`run_ncm_llama_evaluation` for the four isolated blocks, and
`run_ncm_llama_graph` for graph validation. Both `finalize_ncm_llama` and
`finalize_ncm_llama_graph` audit, aggregate and register their own unchanged
decisions. Exact producer commands, versions, source snapshots and input hashes
are retained; use fresh output roots rather than overwriting these runs.

Both local hypothesis records retain `tested:true`, `confirmed:false`; exact,
semantic and full-JSON readback receipts are stored beside their aggregates and
under `data/hypothesis_registry/`. This establishes a smaller, faithful model
for this short synthetic task. It does not establish production95% accuracy,
general Llama capability transfer, unseen-entity quality, mobile performance,
or support for the application's full6300-token inputs and128-token summaries.
