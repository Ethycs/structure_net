# NCM training fits the selected RTX2060 with CPU optimizer state

The two-update lifecycle pilot passed on physical GPU1, the 6GiB RTX2060.
Peak allocated memory was **2,264,888,832 bytes (2.26GB)**; peak PyTorch reserved
memory was **2,348,810,240 bytes (2.35GB)**. The measurements cover model loading,
gradient parity, training, evaluation and strict checkpoint reload. The card's
existing Triton services stayed running. Available GPU memory was tight: the
smallest recorded free memory was 135,135,232 bytes while our allocator held its
reserved pool.

This fit applies to the source-conditioned NCM stage, with original FP32 Llama
features already in host memory. It does not establish that the Llama source
model itself fits alongside the NCM on this card. FP32 weights, FP16 training,
FP32 inference, full input lengths and the native architecture are retained.
AdamW master weights and moments reside in CPU RAM. The complete training set's
17.44GiB feature data uses a separately bounded 24GiB host cache. This cache is a
training optimization and is excluded from application inference-speed claims.

The first pilot stopped after one completed update because its allocation
exceeded the earlier 2.2GB limit. It did not report a CUDA out-of-memory error;
the precise peak was not saved. That failed pilot is preserved unchanged. The
prospective v2 amendment raised the budget to 2.4GB and added memory measurements
before enforcing it. No weights or outcomes from the failed pilot were selected.

The v2 pilot compared packed native teacher forcing with the explicit sequential
calculation on the first and longest training sources, with clean/noisy history.
All trainable gradients passed the fixed parity thresholds and code argmaxes
matched. Both optimizer updates completed with finite gradients. Frozen codec
and word-attention hashes stayed unchanged. Full model, CPU optimizer, scaler,
sampler and random-generator states reloaded exactly and reproduced hard outputs.
The two-update optimizer loop took 3.84 seconds; this tiny warm-cache check is
not a training or application throughput benchmark.

Nine focused CPU checks and the actual CUDA lifecycle passed. The fixed full
2,048-update run and source-disjoint semantic grading are separate stages.
This pilot establishes memory fit, not 95% task accuracy or an inference speedup.
